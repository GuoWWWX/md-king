# md-king 产品需求文档

> 当前目标：把用户每天从 AI 对话、Markdown 文件或 Agent 工作流中产生的 Markdown 内容，快速转换成样式稳定、可继续编辑的 Word/WPS `DOCX` 文档。

## 1. 产品定位

`md-king` 是一个面向 AI 时代的本地桌面文档转换工具。

它首先解决一个高频痛点：用户在 ChatGPT、Claude、DeepSeek、通义、豆包等 AI 工具里得到 Markdown 内容后，需要交付 Word/WPS 文档，但复制到 Word 后样式混乱、标题层级不稳定、表格和代码块难看，每次都要重复调整格式。

产品的一句话定位：

> 把 AI 生成的 Markdown 或本地 `.md` 文件，一键转换成样式稳定、可编辑、可复用模板的 Word/WPS 文档。

## 2. 核心价值顺序

### 2.1 第一优先级：Markdown 转 Word

这是产品必须做好的主能力。

- 用户可以粘贴 Markdown 文本并生成 `DOCX`。
- 用户可以导入或拖拽 `.md` / `.markdown` 文件并生成 `DOCX`。
- 转换结果必须能被 Word/WPS 打开和继续编辑。
- 标题、正文、列表、表格、代码块、引用、链接等常见 Markdown 结构应尽量稳定映射到 Word。
- 用户不需要理解 Pandoc 命令，也不需要手动处理临时文件。

### 2.2 第二优先级：可控的格式与样式

用户需要一定的自定义能力，但不应该被复杂 Word 样式系统吓退。

- 用户可以选择模板，让同一份 Markdown 输出不同风格的 Word 文档。
- 用户可以设置默认模板，减少每次转换前的重复选择。
- 用户可以导入自己的 `reference.docx`，复用学校、公司、客户或个人常用格式。
- 用户可以在应用内调整一部分高频样式，例如标题、正文、表格、代码块、页边距、字体、字号、行距等。
- MVP 阶段应清楚区分“已真实影响 DOCX 输出”的设置和“仅用于预览/草稿”的设置。

### 2.3 第三优先级：模板复用

模板能力是减少重复调样式的关键。

- 内置几类可试用模板，例如通用报告、正式公文、技术文档、论文草稿、商务方案。
- 用户可以快速预览模板适合什么场景。
- 用户可以一键使用某个模板进行转换。
- 用户可以收藏或设为默认模板。
- 后续可以扩展模板市场、团队模板库、模板分享，但不作为当前 MVP 核心。

### 2.4 第四优先级：低摩擦使用入口

用户每天和网页 AI 对话，会反复复制 Markdown 内容。软件应该让这个流程尽量无感。

- 主窗口支持粘贴内容后一键转换。
- 支持从剪贴板读取 Markdown。
- 支持拖入 Markdown 文件。
- 支持悬浮球快捷入口，让用户在浏览器和 AI 对话页面旁边快速转换。
- 悬浮球支持批量拖入 Markdown 文件，也支持粘贴复制的 Markdown 文本。
- 支持全局快捷键唤起快速转换入口。
- 支持在资源管理器选中 `.md` 文件后，通过鼠标右键菜单直接转换。
- 支持命令行调用，方便 Agent、脚本和自动化流程转换 Markdown。
- 支持转换完成后自动打开 DOCX 或打开输出目录。
- 后续支持系统托盘、本地 API、MCP Server 和浏览器扩展。

### 2.5 第五优先级：轻量 Markdown 编辑

产品不是完整 Markdown 编辑器，但需要给用户提供转换前的轻量整理能力。

- 用户可以编辑粘贴进来的 Markdown 内容。
- 支持基本 Markdown 预览或结构检查。
- 支持快速清理常见 AI 输出噪声，例如多余开场白、代码围栏、重复标题。
- 支持基础查找、替换、撤销、统计字数/行数。
- 不在 MVP 阶段追求复杂编辑器能力，例如多人协作、插件系统、完整所见即所得排版。

## 3. 关键用户场景

### 3.1 网页 AI 对话复制转换

用户每天在浏览器里和 AI 对话，得到一段报告、方案、周报或论文草稿。

目标流程：

1. 用户复制 AI 生成的 Markdown。
2. 打开 md-king 或点击悬浮入口。
3. 内容自动进入编辑区或通过“读取剪贴板”进入编辑区。
4. 用户选择模板，或直接使用默认模板。
5. 点击“生成 Word”。
6. 软件输出 DOCX，并可自动打开。

设计要求：

- 主界面第一眼就要让用户知道可以粘贴和生成 Word。
- 默认模板必须可用，不应要求用户先配置。
- 输出路径和模板状态要清楚，但不能干扰主操作。
- 失败时要明确告诉用户原因，例如 Pandoc 不可用、输出目录不存在、模板文件丢失。

### 3.2 本地 Markdown 文件转换

用户已经有 `.md` 文件，需要快速变成 Word/WPS 文档。

目标流程：

1. 用户拖入 `.md` 文件，或点击选择文件。
2. 软件读取内容并展示到编辑区。
3. 用户可选择是否修改内容。
4. 用户选择模板和输出位置。
5. 点击“生成 Word”。

设计要求：

- 文件导入和粘贴内容应进入同一个转换流程。
- 不能让用户在“文件模式”和“粘贴模式”之间感到割裂。
- 文件名可以用于推断默认输出文件名。

### 3.3 Agent 生成 Markdown 后调用转换

用户和本地 Agent 对话，让 Agent 生成 Markdown 文档并转换成 Word。

目标流程：

1. Agent 生成或保存 Markdown。
2. Agent 调用 CLI 或本地 API 发起转换。
3. md-king 返回结构化结果，例如输出路径、是否成功、错误码、警告。
4. Agent 把结果反馈给用户。

设计要求：

- CLI 输出需要支持 JSON。
- 错误码和错误信息要稳定，方便 Agent 判断下一步。
- GUI、CLI、右键菜单、悬浮球后续都应复用同一套转换核心逻辑。
- MVP 可以先在界面展示规划，但不要把未实现能力伪装成已可用。

### 3.4 悬浮球快速转换

用户正在浏览器里和 AI 对话，或者正在桌面整理多个 Markdown 文件，不想打开完整主窗口。

目标流程：

1. 用户把一个或多个 `.md` / `.markdown` 文件拖到悬浮球。
2. 悬浮球展开为轻量转换面板，展示文件数量、当前模板和输出位置。
3. 用户点击“批量生成 Word”。
4. 转换完成后展示成功/失败数量，并提供打开输出目录。

复制文本场景：

1. 用户复制 AI 对话里的 Markdown。
2. 点击悬浮球或使用快捷键唤起快速面板。
3. 粘贴内容或点击“读取剪贴板”。
4. 选择模板后生成 Word。

设计要求：

- 悬浮球不是装饰物，必须服务“拖文件”和“粘贴文本”两件事。
- 批量拖入时要展示任务数量和逐项结果。
- 快速面板不承载复杂设置，只保留模板、输出位置、生成按钮和结果。
- 悬浮球要能最小化，不应遮挡用户正在使用的 AI 网页。

### 3.5 全局快捷键快速转换

用户不想从浏览器切换到主窗口，希望通过快捷键快速处理剪贴板里的 Markdown。

目标流程：

1. 用户复制 AI 生成的 Markdown。
2. 按全局快捷键，例如 `Ctrl+Alt+M`。
3. md-king 弹出快速转换面板，并自动读取剪贴板内容。
4. 用户确认模板后生成 Word。

设计要求：

- 快捷键必须可配置，避免与用户已有快捷键冲突。
- 快捷键触发后应尽量少打断用户。
- 如果剪贴板不是 Markdown，应给出温和提示，而不是直接失败。

### 3.6 右键菜单直接转换

用户在文件夹里已经选中了一个或多个 Markdown 文件，希望不打开主界面直接转换。

目标流程：

1. 用户在 Windows 资源管理器中选中 `.md` / `.markdown` 文件。
2. 右键菜单出现“使用 md-king 转换为 Word”。
3. 点击后使用默认模板和默认输出目录转换。
4. 转换完成后弹出系统通知或打开输出目录。

设计要求：

- 右键菜单只对 Markdown 文件出现，避免污染系统菜单。
- 多文件选择时进入批量转换流程。
- 右键菜单调用 CLI 或统一转换核心，不单独实现转换逻辑。
- 安装和卸载时必须正确注册/清理右键菜单。

### 3.7 命令行与 Agent 调用

命令行是 Agent、脚本和高级用户的主要入口。

目标命令：

```bash
md-king convert ./input.md --template default-report --out ./input.docx --json
md-king convert --stdin --template technical-spec --out ./output.docx --json
md-king batch ./docs --template default-report --out ./dist --json
md-king templates list --json
md-king status --json
```

设计要求：

- 支持文件路径输入。
- 支持标准输入，方便 Agent 直接传 Markdown 内容。
- 支持批量转换。
- 支持 `--json` 输出稳定结构。
- 退出码要稳定：成功为 `0`，转换失败为非 `0`。
- 错误信息要包含输入、输出、模板、错误码和可读提示。

### 3.8 模板试用与复用

用户不想每次进入 Word 手动改标题、字号、缩进、页边距和表格。

目标流程：

1. 用户进入模板中心。
2. 浏览内置模板或导入自己的 `reference.docx`。
3. 选择一个模板试转。
4. 满意后设为默认模板。

设计要求：

- 模板卡片要说明适用场景，而不是只展示名称。
- 模板必须能快速“用于本次转换”和“设为默认”。
- 如果模板没有绑定真实 `reference.docx`，界面必须明确提示。

## 4. MVP 功能范围

### 4.1 必须完成

- 粘贴 Markdown 转 DOCX。
- `.md` / `.markdown` 文件导入转 DOCX。
- 内置 Pandoc 检测和调用。
- 默认输出目录配置。
- 转换结果展示、失败原因展示、打开输出文件。
- 转换历史记录。
- 内置模板列表。
- 导入 `reference.docx` 模板。
- 设置默认模板。
- 轻量 Markdown 编辑区。
- 基础 UI 视觉系统统一。

### 4.2 应该完成

- 从剪贴板读取 Markdown。
- 悬浮球支持粘贴内容快速转换。
- 悬浮球支持批量拖入 Markdown 文件。
- 模板试用流程。
- 输出文件命名预览。
- 转换前内容统计。
- 浏览器预览和桌面真实能力的状态区分。
- 清楚标注规划中的系统集成能力。
- Agent / CLI 的命令草案、JSON 返回结构和错误码设计。

### 4.3 暂不承诺

- 完整 Word 样式可视化编辑器。
- 任意复杂模板的 100% 还原。
- `.doc` 格式直接生成。
- 云端模板市场。
- 账号体系和团队空间。
- 完整 MCP Server。
- 完整系统右键菜单、全局快捷键和托盘能力。
- 富文本所见即所得编辑器。

### 4.4 入口优先级

| 入口 | 目标用户 | MVP 状态 | 说明 |
|---|---|---|---|
| 主窗口转换 | 所有用户 | 必须完成 | 最核心、最稳定的入口 |
| 悬浮球 | 高频 AI 对话用户 | 应该完成基础版 | 支持批量拖文件和粘贴文本 |
| 全局快捷键 | 高频复制转换用户 | 后续接入 | 唤起快速转换面板 |
| 右键菜单 | 本地 Markdown 文件用户 | 后续接入 | 选中文件后直接转换 |
| CLI | Agent / 脚本 / 高级用户 | 需要尽早设计 | 后续实现，但接口设计要先稳定 |
| MCP / 本地 API | Agent 深度集成 | 暂缓 | 等 CLI 稳定后再扩展 |

## 5. 成功标准

### 5.1 用户体验标准

- 新用户打开软件 10 秒内知道如何把 Markdown 变成 Word。
- 默认情况下不需要配置 Pandoc 和模板即可完成一次转换。
- 用户能清楚知道当前使用哪个模板、输出到哪里、转换是否成功。
- 失败时用户知道下一步该做什么。
- UI 看起来像一个专业、轻量、可信的桌面工具，而不是临时拼出来的后台页面。

### 5.2 技术标准

- GUI 和后续 CLI/Agent 使用同一套转换核心。
- 主窗口、悬浮球、快捷键、右键菜单和 CLI 都应调用同一套转换核心。
- 转换结果包含稳定字段：`ok`、`output`、`durationMs`、`warnings`、`errorCode`、`message`。
- 文本输入和文件输入都能走真实 Pandoc 转换。
- 模板解析失败时允许降级到 Pandoc 默认样式，并给出警告。
- 浏览器预览必须明确标记为模拟转换。

## 6. 产品原则

- 主流程优先：任何功能都不能干扰“粘贴/导入 Markdown -> 生成 Word”。
- 本地优先：默认不上传用户文档。
- 能力诚实：没实现的能力可以展示规划，但不能让用户误以为已经生效。
- 模板可感知：用户要能理解模板为什么有价值。
- 样式克制：软件要美观、易懂、专业，但不应喧宾夺主。
- 编辑够用：提供转换前轻量修改能力，不变成完整 Markdown 编辑器。
