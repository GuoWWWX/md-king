# Windows 发布维护

## 工作区清理

合并后删除已完成的远端和本地工作分支，并移除对应 Git worktree。移除前检查未提交文件和分支独有提交；需要保留的历史先保存为仓库外的可验证 Git bundle。截图、日志、临时验证脚本与本机测试产物放在已忽略的 `.codex/`，验收后清理，长期复用的测试归入 `tests/`。

`scripts/` 中保留构建、安装补丁、开发启动与发布流程实际使用的脚本。不要把 `src-tauri/target` 当作废弃工作目录删除；本机可能通过目录联接共用 Rust 构建缓存。清理 worktree 时也应检查 `node_modules` 等联接，避免影响主工作区。

## 版本与分支

1. 将修复合入 `develop`，通过 CI 后同步至 `main`。发版时两条远端分支指向同一提交。`develop` 保存该提交通过检查的前端产物；`main` 校验并复用这些产物，避免再次执行相同构建和测试。
2. 同步 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json` 的版本，并更新浏览器预览 / 更新状态的版本默认值。
3. 等待 `main` CI 成功后推送 `vX.Y.Z` 标签。`main` 已构建并保存 EXE/MSI，Release 工作流优先取回同一提交的安装包，校验后继续生成差分、签名和发布。手动运行工作流时输入已存在的版本标签。
4. 确认 Release 包含 EXE、MSI、`update-manifest.json`、`update-manifest.sig`、`SHA256SUMS.txt`，并检查工作流成功状态。工作流还会尝试为上一稳定版本生成差分包；只有可精确还原且节省至少 10% 时才发布 `.patch`，否则保留完整包更新。

EXE/MSI 安装包只上传到 GitHub Releases，不提交到 Git 源码仓库。构建缓存和发布输出位于已忽略的 `src-tauri/target/`。内置 Pandoc 的 `src-tauri/resources/pandoc/windows/pandoc.exe` 是构建所需资源，通过 Git LFS 管理，应继续保留。

## 检查与构建复用

复用只接受本仓库 `.github/workflows/ci.yml` 在指定来源分支上成功完成的 push 运行，提交必须与当前检出的提交完全一致；不使用 PR、其他分支或 fork 的产物。Artifact 按提交和运行次数命名，保存 7 天，并记录版本、提交、所有前端文件或安装包的大小及 SHA-256。下载后逐项验证，校验失败立即停止。

产物缺失或过期时，CI / Release 执行完整检查和构建；旧标签没有复用脚本时也走原有流程。依赖审计每次重新执行。发布阶段的版本、公私钥匹配检查、更新清单签名和差分还原 SHA-256 校验不跳过。

`pnpm tauri:build` 先让 Tauri 生成不压缩的临时 NSIS 安装包及脚本，再应用全部安装补丁，最后只执行一次非 solid LZMA 压缩。临时包不上传；任何补丁或编译失败都会中止。`main` 已持有验证过的前端产物，调用 `pnpm tauri:build -SkipFrontendBuild` 避免重复构建前端。发布复用时也无需再次准备 Rust 或拉取 Pandoc。

修改此流程后运行 `pnpm test:release`，检查来源筛选、损坏产物拒绝、安装器压缩和签名保护；并通过一次完整 Windows 打包及差分还原验证。GitHub 工作流还应通过 actionlint 检查。

要实际验证跨工作流复用，等待 `main` CI 成功后手动运行 Release，输入当前 `main` 的 `vX.Y.Z` 版本并勾选 `verify_only`。该模式检出 `main`，执行安装包复用、差分还原和真实签名校验，只保存验证元数据，不创建标签，也不创建或修改 GitHub Release。

工作流通过 `RELEASE_TAG` 将待签名版本传给签名脚本，避免手动运行时 GitHub 预置的 `GITHUB_REF_NAME` 仍指向分支。签名脚本继续严格检查该版本与项目版本一致。

## 更新签名密钥

本项目使用 Ed25519 对更新清单的原始 UTF-8 字节签名。清单包含版本、安装包文件名、大小和 SHA-256。客户端固定可信仓库地址、校验清单签名，并在安装前再次校验文件。

清单的可选 `delta` 字段一并签名，包含基准版本、基准安装包大小和 SHA-256，以及差分包文件名、大小和 SHA-256。发布后还应核对这些值与 GitHub 资产及 `SHA256SUMS.txt` 一致。安装器缓存自身供后续差分还原；旧客户端首次升级仍使用完整包，没有匹配基准或差分无法使用时也下载完整包。Pandoc 根据本地文件及版本标记决定复用或补装。

- 客户端公钥：`src-tauri/update-public-key.txt`，Base64 编码的 32 字节公钥。
- 仓库 Secret：`UPDATE_SIGNING_PRIVATE_KEY`，Base64 编码的 PKCS#8 DER 私钥。
- 维护者本机备份：Codex 用户目录下的 `secrets/md-king/update-signing-key.der`。请保留离线备份，不要上传到仓库、Issue 或公开日志。
- 本地签名：在当前进程中读取私钥并设置该环境变量，然后执行 `node scripts/sign-update.mjs`；结束后清除进程中的环境变量。不要打印私钥或将其写入命令历史。

Release 工作流缺少私钥、版本不匹配、构建失败或公私钥不匹配时停止发布。签名保证安装包与维护者发布的清单一致；它不是 Windows Authenticode 代码签名，系统仍可能显示发布者 / 权限确认。

已发版客户端内置旧公钥。不要直接替换密钥后发布，否则旧客户端会拒绝更新；轮换前需要设计兼容迁移版本。

## 安装与验收

首次启动在首屏显示后 3 秒静默检查更新；从托盘恢复主窗口或再次双击程序时也会检查，不需要等待后台的 4 小时轮询。静默检查只显示侧栏提示，用户点击后才进入下载和安装。下载途中可在弹窗手动检测新版；检测本身不取消当前下载，点击下载更高版本后才清理旧下载。取消、断网或重启后可续传同一签名清单对应的下载。

NSIS 包用于应用内更新；MSI 供手动安装使用。更新参数为 `/S /UPDATE /R /D=<当前可执行文件所在目录>`，其中 `/D` 必须放在最后。更新前持久化草稿会话，安装程序启动失败时保留当前应用。

手动运行 EXE 安装包时，检测到旧 NSIS 版本会显示“覆盖安装（保留原安装，推荐）”，并默认选中；同版本可选择“覆盖安装 / 修复当前版本”。覆盖安装直接更新原目录，不先运行卸载程序。仍保留“先卸载再安装”供用户主动选择。已有 MSI 版迁移到 EXE 版时，Tauri 会先调用 Windows Installer 移除 MSI；迁移页面不提供覆盖选项，以免误导用户。

验收检查：旧版本发现新版本 → 左侧提示 → 进度、取消和重试 → 签名 / 哈希校验 → 覆盖原目录 → 自动重启 → 关于页显示新版本。校验失败不得执行安装包。
