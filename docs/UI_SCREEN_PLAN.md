# md-king 界面设计规划

> 目标：先把页面结构和界面方向设计清楚，再逐步改代码。当前优先服务“粘贴/导入 Markdown -> 选择模板 -> 生成 Word -> 查看结果”这条主链路。

## 1. 设计方向

md-king 应该像一个专业、轻量、长期可用的桌面效率工具。

当前已选定主视觉方向为 **Variant C：柔和玻光蓝**。后续页面实现以 [UI 风格方向](UI_STYLE_DIRECTION.md) 和 [design-assets](design-assets/README.md) 中的 C 风格设计稿为准。

关键词：

- 专业
- 干净
- 稳定
- 易懂
- 本地安全
- 文档工具感
- AI 工作流友好

避免：

- 大面积高饱和紫色。
- 过多卡片套卡片。
- 像后台管理系统一样堆设置项。
- 把规划中的功能做得像已经可用。
- 让用户先理解概念再开始转换。

## 2. 全局信息架构

主窗口采用：

```text
左侧导航 + 顶部状态栏 + 页面标题区 + 主内容区
```

建议导航：

1. 转换
2. 模板
3. 历史
4. 快速入口
5. Agent / CLI
6. 设置
7. 关于

其中 MVP 阶段优先完成：

- 转换
- 模板
- 历史
- 设置

`快速入口`、`Agent / CLI` 可以保留为规划页面，但必须明确标注当前状态。

## 3. 全局状态栏

顶部状态栏只显示和当前转换可信度强相关的信息。

建议展示：

- Pandoc：可用 / 待检测 / 不可用
- 当前模板：模板名称
- 输出位置：默认目录或与源文件同目录
- 运行模式：桌面真实转换 / 浏览器预览模拟

不建议展示：

- 太多营销标签。
- 不影响当前操作的装饰性徽标。
- 未实现能力的强提示。

## 4. 页面一：转换工作台

这是最重要页面，优先重做。

### 4.1 页面目标

用户打开软件后，第一眼就知道：

- 可以粘贴 Markdown。
- 可以导入 Markdown 文件。
- 可以选择模板。
- 可以生成 Word。
- 可以看到生成结果。

### 4.2 推荐布局

```text
┌────────────────────────────────────────────────────────────┐
│ 转换工作台                                                   │
│ 粘贴 AI Markdown 或导入 .md 文件，生成可编辑 DOCX。            │
├────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────────────────┐ ┌───────────────┐ │
│ │ Markdown 编辑区                       │ │ 转换面板       │ │
│ │                                      │ │ 模板           │ │
│ │ [粘贴 / 导入 / 读取剪贴板]             │ │ 输出位置       │ │
│ │                                      │ │ 文件名预览     │ │
│ │ 文本编辑区                            │ │ [生成 Word]    │ │
│ │                                      │ │ 状态/警告      │ │
│ └──────────────────────────────────────┘ └───────────────┘ │
│ ┌────────────────────────────────────────────────────────┐ │
│ │ 转换结果 / 最近一次输出                                  │ │
│ └────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────┘
```

### 4.3 关键设计调整

- 把模板选择、输出目录、输出文件名、生成按钮放到右侧固定转换面板。
- 编辑区可以大，但不能把转换按钮挤到不显眼的位置。
- 结果区优先展示最近一次转换结果，而不是长期历史列表。
- 最近任务可以收起或放到历史页，不应抢主流程注意力。
- 粘贴、导入文件、读取剪贴板是同一编辑区的三个入口。
- 如果当前是浏览器预览，要在转换面板明确提示“模拟转换，不生成真实 DOCX”。

### 4.4 编辑区能力

MVP 编辑区建议支持：

- 粘贴和直接编辑 Markdown。
- 导入文件后填充到编辑区。
- 从剪贴板读取。
- 字符数、行数、标题数统计。
- 清空内容。
- 后续支持查找替换、格式清理、Markdown 预览。

### 4.5 转换面板字段

转换面板建议包含：

- 当前模板。
- 输出位置。
- 输出文件名。
- 转换后自动打开。
- 是否覆盖同名文件。
- 主按钮：生成 Word。
- 次按钮：打开模板页 / 打开设置。

其中“生成 Word”必须是页面最清楚的行动按钮。

## 5. 页面二：模板中心

### 5.1 页面目标

让用户理解模板可以减少重复调样式，并快速试用模板。

### 5.2 推荐布局

```text
┌────────────────────────────────────────────────────────────┐
│ 模板中心                                                     │
│ 选择或导入 reference.docx，让 Markdown 输出不同 Word 风格。    │
├────────────────────────────────────────────────────────────┤
│ 筛选：全部 / 报告 / 公文 / 技术 / 我的模板                     │
│ [导入模板] [创建样式草稿]                                     │
├────────────────────────────────────────────────────────────┤
│ 模板卡片网格                                                   │
│ ┌──────────┐ ┌──────────┐ ┌──────────┐                       │
│ │ 通用报告 │ │ 正式公文 │ │ 技术文档 │                       │
│ │ 场景说明 │ │ 场景说明 │ │ 场景说明 │                       │
│ │ 试用/默认│ │ 试用/默认│ │ 试用/默认│                       │
│ └──────────┘ └──────────┘ └──────────┘                       │
└────────────────────────────────────────────────────────────┘
```

### 5.3 模板卡片信息

每张模板卡片需要展示：

- 模板名称。
- 适用场景。
- 是否内置。
- 是否绑定真实 `reference.docx`。
- 是否默认模板。
- 操作：用于本次转换、设为默认、编辑样式、删除。

### 5.4 模板能力诚实表达

- 内置模板如果没有真实 `reference.docx`，应标注“使用 Pandoc 默认样式”。
- 样式管理器如果尚未写回 DOCX，应标注“当前影响预览/草稿，DOCX 写回待接入”。
- 导入模板必须清楚说明导入的是 Word 样式参考文件。

## 6. 页面三：样式编辑器

### 6.1 页面目标

让用户具备一定自定义格式能力，但不暴露完整 Word 样式复杂度。

### 6.2 MVP 范围

优先做高频样式：

- 标题 1 / 2 / 3。
- 正文。
- 表格。
- 代码块。
- 引用。
- 页边距和基础字体。

### 6.3 推荐布局

```text
┌────────────────────────────────────────────────────────────┐
│ 样式编辑器：通用报告模板                                     │
├────────────────────────────────────────────────────────────┤
│ 左侧：样式列表        中间：属性编辑        右侧：Word 预览     │
│ 标题 1               字体/字号/颜色          示例文档片段       │
│ 标题 2               行距/间距/缩进                            │
│ 正文                 表格边框/表头                              │
└────────────────────────────────────────────────────────────┘
```

### 6.4 设计原则

- 不让用户直接面对所有 Word 样式概念。
- 默认给“推荐预设”，再允许细调。
- 每次修改都要能在预览里立即看见效果。
- 保存时明确说明是否已经影响真实 DOCX 输出。

## 7. 页面四：历史记录

### 7.1 页面目标

让用户快速找到最近生成的 DOCX，重新打开、复制路径或定位失败原因。

### 7.2 推荐功能

- 按成功/失败筛选。
- 搜索输入文件、输出文件、模板名。
- 打开输出文件。
- 打开所在目录。
- 复制输出路径。
- 重新转换。
- 清空历史。

历史页不应该像日志系统，重点是“找回刚刚生成的文档”。

## 8. 页面五：快速入口

### 8.1 页面目标

服务用户每天和网页 AI 对话时的低摩擦转换。

快速入口页要讲清楚四类入口：

- 悬浮球。
- 全局快捷键。
- Windows 右键菜单。
- 命令行 / Agent。

### 8.2 悬浮球设计

如果悬浮球已经能用，则该页展示：

- 是否启用悬浮球。
- 当前模板。
- 默认输出位置。
- 支持的输入方式。
- 最近一次快速转换结果。

悬浮球展开后的轻量面板建议：

```text
┌────────────────────────────┐
│ 快速转换                    │
│ 拖入 Markdown 文件或粘贴内容 │
├────────────────────────────┤
│ [拖入区 / 粘贴区]            │
│ 当前：3 个 Markdown 文件      │
│ 模板：默认报告模板            │
│ 输出：与源文件同目录          │
├────────────────────────────┤
│ [批量生成 Word]              │
└────────────────────────────┘
```

悬浮球必须支持：

- 单个 Markdown 文件拖入。
- 多个 Markdown 文件批量拖入。
- 粘贴复制的 Markdown 文本。
- 读取剪贴板。
- 展示成功/失败数量。
- 打开输出目录。

悬浮球不建议承载：

- 完整模板管理。
- 复杂样式编辑。
- 长历史列表。
- 过多设置项。

### 8.3 全局快捷键设计

快捷键用于快速唤起悬浮转换面板。

推荐默认行为：

- 默认快捷键：`Ctrl+Alt+M`。
- 用户按下快捷键后，打开快速转换面板。
- 如果剪贴板有 Markdown，自动填入面板。
- 如果剪贴板为空或不是 Markdown，面板显示粘贴区。

设置页需要提供：

- 启用/停用快捷键。
- 修改快捷键。
- 快捷键冲突提示。

如果全局快捷键尚未实现，只展示“规划中”，不要提供可保存但无效的开关。

### 8.4 Windows 右键菜单设计

右键菜单用于本地 Markdown 文件转换。

菜单项建议：

```text
使用 md-king 转换为 Word
使用 md-king 转换为 Word...
```

两种行为：

- 直接转换：使用默认模板和默认输出目录。
- 打开转换窗口：带着选中文件进入主窗口确认。

多文件场景：

- 显示批量任务数量。
- 使用默认模板。
- 转换完成后显示成功/失败结果。

设计要求：

- 只在 `.md` / `.markdown` 文件上出现。
- 安装器负责注册，卸载时清理。
- UI 中展示状态：未安装 / 已注册 / 注册失败。

### 8.5 命令行 / Agent 入口设计

命令行页面要让 Agent 和高级用户直接知道怎么调用。

页面建议包含：

- CLI 当前状态。
- 常用命令。
- JSON 输出示例。
- 错误码说明。
- Agent 调用建议。

命令示例：

```bash
md-king convert ./input.md --template default-report --out ./input.docx --json
md-king convert --stdin --template technical-spec --out ./output.docx --json
md-king batch ./docs --out ./dist --template default-report --json
```

JSON 示例：

```json
{
  "ok": true,
  "input": "D:/docs/input.md",
  "output": "D:/docs/input.docx",
  "templateId": "default-report",
  "durationMs": 842,
  "warnings": []
}
```

如果 CLI 尚未实现，该页面必须明确标注“规划中”，但可以先固定命令设计，避免后续反复改 Agent 调用方式。

### 8.6 后续入口

- 悬浮球。
- 全局快捷键。
- 系统托盘。
- Windows 右键菜单。
- 命令行。
- 浏览器扩展。

其中浏览器扩展是长期方向，可让用户在 AI 网页中直接点击“转 Word”。

## 9. 页面六：Agent / CLI

### 9.1 页面目标

让高级用户和 Agent 知道如何通过命令调用 md-king。

### 9.2 推荐内容

- 当前实现状态。
- 示例命令。
- JSON 输出示例。
- 常见错误码。
- 后续 MCP Server 规划。

如果 CLI 尚未实现，页面标题和主状态必须明确写“规划中”，避免误导。

## 10. 页面七：设置

### 10.1 页面目标

设置页只承载低频配置，不承载主转换流程。

### 10.2 建议分组

- 转换默认值：输出目录、打开文件、同名处理。
- Pandoc 引擎：内置 Pandoc、自定义路径、检测状态。
- 外观：主题、主题色。
- 数据：历史记录、日志。
- 系统集成：只展示真实可用入口，未完成入口标注规划。

### 10.3 设计调整

- 保存按钮不需要做成大面积强色块。
- 未保存状态可以用轻提示，不要抢主页面层级。
- 设置项用分组列表即可，不需要每组都做厚重卡片。

## 11. 视觉系统建议

> 更新：当前视觉系统已从早期“冷灰 + 低饱和靛蓝”收敛到“柔和玻光蓝”。本节原则仍有效，但具体 token 以 [UI_STYLE_DIRECTION.md](UI_STYLE_DIRECTION.md) 为准。

### 11.1 颜色

建议默认从当前紫色转向更稳的办公工具色：

- 主色：专业蓝或低饱和靛蓝。
- 背景：接近白色的冷灰。
- 成功：绿色。
- 警告：琥珀色。
- 错误：红色。

主色只用于：

- 当前导航项。
- 主行动按钮。
- 关键焦点状态。
- 少量高优先级状态。

### 11.2 圆角

统一圆角规则：

- 页面面板：`12px`。
- 输入框和按钮：`8px`。
- 小徽标：`999px`。

不要在同一层级混用大量 `rounded-lg`、`rounded-xl`、`rounded-2xl`。

### 11.3 卡片

卡片只用于清楚分组，不用于堆装饰。

- 主转换编辑区可以是大面板。
- 转换设置可以是固定侧栏面板。
- 设置页可减少卡片数量，改成更轻的分区。

### 11.4 文案

按钮和标题要直接：

- 生成 Word
- 读取剪贴板
- 导入 Markdown
- 选择模板
- 打开 DOCX
- 设为默认

避免抽象文案：

- 工作区
- 控制台
- 智能增强
- 工作流

除非这些能力已经真的存在。

## 12. 页面设计优先级

建议按这个顺序推进：

1. 重做转换工作台。
2. 统一视觉 token 和基础组件风格。
3. 调整模板中心，让模板价值更清楚。
4. 调整设置页，降低视觉噪声和规划能力误导。
5. 完善历史页的找回和重试能力。
6. 再设计快速入口和 Agent / CLI 页面。

## 13. 第一阶段验收标准

- 用户无需进入设置页即可完成一次转换。
- 生成 Word 按钮在转换页始终清楚可见。
- 当前模板、输出位置、输出文件名清楚可见。
- 转换成功后能看到输出路径和打开按钮。
- 浏览器模拟和桌面真实转换状态清楚区分。
- 规划功能不会以可用开关形式误导用户。
- 页面视觉统一，不再依赖全局覆盖 Tailwind 颜色类。
